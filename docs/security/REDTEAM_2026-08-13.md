## P1-1 — Closed-beta gate is “any Supabase session,” not invite/password

| Field | Detail |
|-------|--------|
| **Severity** | P1 |
| **File / symbol** | `app/auth/callback/route.ts` (`GET`) · `app/api/private-access/session/route.ts` (`POST`) · `src/lib/privateGate.ts` (`hasVerifiedSupabaseUser`) · `src/lib/publicRoutes.ts` (`PRIVATE_GATE_PUBLIC_PATHS` includes `/auth/callback`) |
| **Impact** | A verified Supabase user is treated as a full private-gate pass, and the auth callback (and the session-mint route) write a 30-day `mw_private_access` cookie with no invite redeem and no allowlist. |
| **Blue-team fix** | While `PRIVATE_MODE` is on, mint the gate cookie only after an invite (or founder password) is bound to that user id; do not treat “has a JWT” as “was invited.” Keep F1’s `getUser()` verification — change *who* is eligible, not *how* the JWT is checked. |

F1 (2026-08-05) correctly stopped trusting decoded JWT payloads. It also made **any** verified session a gate key. `/welcome` and `/auth/callback` stay reachable while gated; `NEXT_PUBLIC_SUPABASE_*` is on every public page. Signup is not invite-bound on the server. The password form on `/private` is then optional.

## P1-2 — Territory hard-block trusts client-settable country headers

| Field | Detail |
|-------|--------|
| **Severity** | P1 |
| **File / symbol** | `src/lib/legal/supportedRegions.ts` (`hostedServiceAccessFromHeaders`, `countryFromRequestHeaders`) · callers: `app/api/checkout/route.ts`, `app/api/crypto-checkout/intent/route.ts`, `app/api/geo/route.ts` |
| **Impact** | The in-app Europe / OIC / CA / UA / unknown-edge block can be decided from `cf-ipcountry` or `x-country-code` even when Vercel has already set a real `x-vercel-ip-country`. Missing country is treated as allow. |
| **Blue-team fix** | On Vercel, trust only `x-vercel-ip-country` (overwrite, do not prefer a `cf-ipcountry` the client can send). Drop `x-country-code`. Fail closed when the platform country header is absent in production. Do not let a spoofed CF header win over the platform header (the unit test currently pins that preference). **Closed `.779`.** |

The block itself is a product rule. The defect is that checkout, crypto intent, and `/api/geo` share a helper that prefers a spoofable header and fail-opens on “no country.” Cloudflare edge rules, if present, are a separate layer — this is the in-app hard block the legal copy claims.

## P1-3 — Hosted signup geo-check is UI-only

| Field | Detail |
|-------|--------|
| **Severity** | P1 |

## P1-4 — Mobile Coach APIs treat unset `PRIVATE_MODE` as public

| Field | Detail |
|-------|--------|
| **Severity** | P1 |
| **File / symbol** | `src/lib/mobileAccess.ts` (`allowMobileCoachBootstrap`) · `app/api/mobile/coach/plan/route.ts` · `app/api/mobile/coach/adapt/route.ts` |
| **Impact** | Web `isPrivateModeEnabled()` is **on** when `PRIVATE_MODE` is unset in production. Mobile bootstrap is **open** unless the string is exactly `'true'`. Preview and prod that rely on the default-on gate still serve unauthenticated seed/adapt Coach JSON. |
| **Blue-team fix** | Call `isPrivateModeEnabled()` (same helper as `proxy.ts`). Do not compare `process.env.PRIVATE_MODE === 'true'` / `!== 'true'` in a second place. |

These routes return generated plans, not another athlete’s logs. The bug is gate consistency, not IDOR.

## P1-5 — Shared-device local state is not account-scoped

| Field | Detail |
|-------|--------|
| **Severity** | P1 |
| **File / symbol** | `src/lib/journeySync.ts` (`syncJourneyOnSignIn`, `mergeJourneyStates`, `pushJourneyToCloud`) · `src/page-components/AccountPage.tsx` (`handleSignOut`) · `src/lib/storage/keys.ts` (unprefixed `mw_*` keys) · `src/page-components/AssessmentsPage.tsx` (`saveNutritionEntry`) |
| **Impact** | Sign-out does not clear device storage. The next sign-in merges guest/prior journey (including `readiness.parq`) with OR-logic and upserts it onto that account. A signed-in PAR-Q submit also writes `Assessment: {risk} risk` into `nutrition_logs`. |
| **Blue-team fix** | Namespace or wipe athlete-local keys on sign-out / before a different user id signs in. Push journey only after an explicit “keep this device’s progress” prompt. Stop writing health-screen results into the food-log table. **Closed `.774`** (wipe + owner bind; guest health stripped rather than a keep-progress prompt). |

This is the guest vs signed-in leak on this tip. `syncCurrentHistoryToCloud` has no callers; workout attach is latent. Journey + PAR-Q attach is live.

## P2-1 — Account delete accepts an unproven `deviceId`

| Field | Detail |
|-------|--------|
| **Severity** | P2 |
| **File / symbol** | `src/lib/accountDataServer.ts` (`deleteAccount`) · `app/api/account/delete/route.ts` |
| **Impact** | A signed-in caller can pass any `deviceId` and delete *anonymous* `push_subscriptions` and `llm_usage` rows for that device. Rows with a `user_id` are not touched. Device ids are UUIDs but are sent to many APIs and sit in `localStorage`. |
| **Blue-team fix** | Ignore client `deviceId` unless it is already linked to this `user_id`, or only delete anonymous rows for a server-known device from this session. **Closed `.775`.** |

Export correctly refuses client device ids. Delete does not.

## P2-2 — PAR-Q risk is stored as a nutrition row

| Field | Detail |
|-------|--------|
| **Severity** | P2 |
| **File / symbol** | `src/page-components/AssessmentsPage.tsx` (`submitAssessment` → `saveNutritionEntry`) |
| **Impact** | Health-screen risk (`low` / `moderate` / `high`) is inserted into `nutrition_logs` as a food name when the athlete is signed in, then appears in GDPR export and any nutrition reader. |
| **Blue-team fix** | Persist assessment only in `mw_last_assessment` (and a dedicated column if cloud is required). Never reuse the food-log write path. **Closed `.773`.** |

PostHog’s typed events do not include pregnancy/PT flags (those symbols are **not on this tip** — see Hunt closed). This is the health-flag leak that *is* present: risk string into the wrong table, plus journey `parq: true` on the profile (P1-5).

## P2-4 — Wearables OAuth state HMAC has a hardcoded fallback secret

| Field | Detail |
|-------|--------|
| **Severity** | P2 |
| **File / symbol** | `src/lib/wearables/oauthState.ts` (`secret`) |
| **Impact** | If `WEARABLES_OAUTH_STATE_SECRET`, `PRIVATE_ACCESS_SECRET`, and `NUDGE_SECRET` are all unset, state is signed with a repo-visible fallback. Wearables are flag-off today; the fallback is still a forgeable state if the surface is enabled on a misconfigured Preview. |

## P2-5 — Territory client fail-open and session-caches “allowed”

| Field | Detail |
|-------|--------|
| **Severity** | P2 |
| **File / symbol** | `src/lib/legal/territoryAccessClient.ts` (`fetchTerritoryAccess`) |
| **Impact** | A failed `/api/geo` response is treated as `blocked: false` (not cached). A successful “allowed” decision — including missing-country allow from P1-2 — is stored in `sessionStorage` for the tab, so SignInPanel / UnlockButton skip the UI block. |
