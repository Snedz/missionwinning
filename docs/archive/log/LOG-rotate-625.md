## 2026-08-08 — The Athlete Card: identity you can wear and send (`.610`)

**The product had ten ranks and thirteen medallions and no way to wear any of it.**

Asked to improve the social aspect, citing MySpace and WeChat. Three audits found the shape of it: **exactly one mechanic in the entire codebase puts one human's data on another human's screen** — the `leaderboard_snapshots` table. No follows, friends, feed, comments, likes, posts or memberships table exists, and no dead code for any. Meanwhile **1 of 19 profile cards was identity**: no avatar, no display name on `/profile`, no public profile, and the only editable expressive string in the product was a 24-character "Call sign" on a different screen. Rank and badges lived in `localStorage`, invisible to a second device, let alone a second person.

**What this is not.** Not a feed, comments or DMs — and not because a doc refuses them. A feed needs density the product does not have; moderation is an *operational* cost that lands on one person forever; and it would trade away the thing that makes this product distinct. `shareCard.ts` already had the better answer in its header: *"Hevy's loop is an in-app social feed; ours is share OUT."*

**The correction that shaped it.** The first instinct was cloud-persisted rewards so rank survives a device wipe. Wrong twice: it is **a client grant API** — upload your own XP and you can forge your own rank, the invariant `CLUB_PLAN.md:72` names exactly — and it is **unnecessary**, since every XP source is already server-visible, so cloud rewards is a *recompute*, not a sync. The card therefore ships **100% locally**: no table, no migration, no route, no policy change, nothing new leaving the device. Roughly 80% of the value at none of the risk, and it decouples the best idea from the riskiest one.

**Customization inside a design system that forbids decoration.** No gradients, no glows, no shadows, radius 0, four grays and three reds. So what an athlete unlocks is the system's own vocabulary getting denser — hairline → rule → double rule → poster; paper → grid → rule field → poster block. Off-palette is impossible because those are the only values in the file. And **picks-from-sets means no free text and no uploads**, which is what makes it moderation-safe by construction rather than by policing.

**The clamp is the whole security model.** `resolveCardCosmetics` lives in `packages/mw-core` (Android needs the identical mapping) and answers one question: may this athlete render this pick? The config is athlete-editable — `localStorage` today, a `jsonb` column the day a card syncs — so it can name a tier-4 frame at tier 1. Resolution falls back to the earned default rather than rendering the locked pick, and owned badges are passed in rather than trusted from the config, because a badge is the one thing on a shared PNG that another person cannot check. **No unlocks table:** unlocks are deterministic from tier, so a table would be a denormalized copy that can disagree with the function.

The card's data follows the honesty rules the other share surfaces already have: a quiet week prints no "0 sessions" row (`ScoreNumeral`'s rule — a zero reads as failure), and `prLine` stays null rather than invent something, exactly as `pickHeadlinePr` does.
