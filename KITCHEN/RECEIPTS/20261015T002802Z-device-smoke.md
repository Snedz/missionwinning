## Dead ends and blockers found

### 1. `npm run verify` health step fails on a busy machine (fixed, PR)
```
FAIL  health     60.3s
▶ health: next start -p 3917 → GET /api/health
  no response
```
Not a product defect. Another agent's process (AutoClaw, PID 44030) holds
`127.0.0.1:3917`, and `verify.mjs` guards with `probe.listen(port, '0.0.0.0')` — which
**succeeds on macOS even when loopback is taken**, so the guard reported "free",
`next start` could not get the port, and the probe burned its full 60 s printing a bare
`no response`.

Reproduced directly:
```
$ node -e "...listen(3917,'0.0.0.0')"   # with AutoClaw squatting on 127.0.0.1:3917
GUARD SAYS FREE  <-- false negative
```

Proof the product is fine — same tree, free port:
```
$ VERIFY_PORT=4477 npm run verify
PASS build-label / typecheck / lint / test / build     VERIFY: PASS
$ curl http://127.0.0.1:4477/api/health
{"ok":true,"build":"2026.07-unified.1134",...}          HTTP 200
```

### 2. The coach never answers: a length guard silently discards the reply (fixed, PR)
`CoachViewModel.askTrainer` → `POST /api/coach/trainer` → `replyTrainer`. On device
this showed **"Trainer is offline."** — a graceful message, not a crash, but the coach
was dead.

Root cause chain, each step measured:
- `app/api/coach/trainer/route.ts` reads a provider via `resolveCoachProviders`, seat
  order Groq → `COACH_LLM_*` → OpenRouter `:free`, else the `rules` line.
- The provider client posts to **`seat.url` verbatim**, so `COACH_LLM_API_URL` must be
  the *full* chat-completions URL, not the base. Passing `.../4001/v1` 404s. (Env-var
  documentation issue, not a crash.)
- With the full URL the model answered: `ok:true, status:200, 211 completion tokens`.
- **But the route still returned `source:"rules"`.** `acceptModelText` discarded any
  reply **over 420 characters**, so a verbose local model always lost and the fallback
  was used silently. The user sees "Trainer is offline" while a good reply sits in the
  response.

After the fix, with no provider key anywhere and the lane serving Ollama locally:
```
Q: Should I add weight next session?
  source: coach_llm | model: auto | len: 420
  "Based on the information provided, it seems like you're following a bodyweight
   squat routine... To determine if you should add weight next session, consider..."

Q: How many rest days do I need?
  source: coach_llm | model: auto | len: 404
```

### 3. Debug build points at production, so the device can never reach a local server
`apps/android/app/build.gradle.kts` defaults `mw.apiBaseUrl` to
`https://www.missionwinning.com`. The debug APK I installed therefore calls production
with no auth, and `CoachPlanRepository.askTrainer` returns
`Result.failure(IllegalStateException("coach offline"))` → "Trainer is offline."
A developer testing the coach locally must know to set `mw.apiBaseUrl` in the
gitignored `local.properties`. Not fixed here — it is a documentation/ergonomics
issue, and changing the default would point debug builds somewhere wrong by surprise.

## Setup notes (each cost real time; worth writing down)

- **The debug package is `com.missionwinning.app.debug`**, not `com.missionwinning.app`
  (`applicationIdSuffix = ".debug"`). `adb shell monkey -p com.missionwinning.app`
  fails with *"No activities found to run"*, which reads exactly like a broken manifest
  and is not. Launch with
  `am start -n com.missionwinning.app.debug/com.missionwinning.app.MainActivity`.
- **`adb shell input tap` takes device pixels.** Screenshots come back 1080×2400 but are
  displayed at 900×2000; tapping the displayed coordinate silently misses. Multiply by 1.2.
- `sdkmanager` needs `JAVA_HOME` explicitly; without it: *"Unable to locate a Java Runtime"*.
- The AVD needed its userdata partition shrunk (`disk.dataPartition.size`) to boot on a
  disk with ~6 GB free.
