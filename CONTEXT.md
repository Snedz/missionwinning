Benchmarked: 200 sessions = 647 KB / 3.45 ms, 500 = 1.6 MB / 9.64 ms; a mid-tier Android is 4–6× slower and the disk write costs as much again — **30–50 ms of blocked main thread per second while logging, 60–100 ms/s during rest**, on the wedge screen, mid-set, on the cheapest phone in the target market. **Two halves**: `elapsedSeconds` leaves `partialize` and is **derived from `activeWorkout.startedAt`** (also more correct — the counter froze while the tab was closed, so a session resumed after twenty minutes reported tab-open time, not training time); and [`dedupeWrites`](src/store/persistDedupe.ts) skips any `setItem` whose bytes are already on disk. A tick now produces an identical payload and is skipped outright. **Throttling deliberately not added**: this is the path that holds sessions nobody can reproduce from memory (`.205` was the last defect here), a deferred write that fails to flush is data loss, and the events that would flush it fire unreliably on mobile — whereas skipping a byte-identical write *cannot* lose anything, because the value on disk is already the value being written. Four mutants killed. **Two self-inflicted misses**: the SSR fallback shipped as `undefined!` and killed every store test; and the wiring guard's slice matched the `WorkoutState` **interface** 400 lines above the implementation, producing a backwards slice that asserted on an empty string — sixth and seventh vacuous guards in this programme, both minutes old. Tests 1066→1078. **`/active` render cost carried forward** — per-set history scan, two `localStorage` reads in render, `localeCompare` sort per tick: re-render work, not disk writes, and belongs with a `React.memo` pass.
- **306 KB of translations on every route (`.209`):** measured, not estimated — the largest user-visible win in the wave. [`localeHttpLoader.ts`](src/lib/localeHttpLoader.ts) needed two metadata fields per namespace and got them by importing `LOCALE_EXPORTS`, which pulls 28 `*Locales.ts` modules **and** `localePacks`'s 14 JSON packs (1.1 MB on disk) — and it is reached from the **root layout**, so `app/layout.tsx → I18nPwaProvider → LocaleHttpSync → localeHttpLoader → exportLocales → localePacks` was entirely static. One `chunks/7660-…js` at **1,053,845 B raw / 313,839 B gzipped**, a plain `<script async>` on `/`, `/log` *and* `/active` — **44 % of the initial JS on the logger**. An English user in Nairobi on 3G downloaded Thai, Vietnamese and Hindi before first paint. `hydrateResources.ts` and `src/i18n.ts` both carry headers claiming the opposite: **true of the source, false of the build**, which is exactly why a byte budget beats a comment. Fix is [`localeExportManifest.ts`](src/i18n/localeExportManifest.ts) with **zero imports**; `exportLocales` derives `LocaleNamespace` from it so the list exists once. After: `/log` **264.3 KB**, `/active` **420.3 KB**, `/` **247.4 KB** gzipped, the megachunk gone from the build, and a byte scan of every chunk still on `/log` finds **no locale-pack strings** (checked for `Platos`, `ครั้ง`, `तकरार` rather than trusting a chunk name). **The missing gate step now exists**: [`bundle-budget.mjs`](scripts/bundle-budget.mjs) reads the *prerendered HTML* — which `<script>` tags the browser actually fetches, not what the graph contains — runs after the build, ratchets down only (`.202` shape), and **fails rather than passes when `.next/` is absent**. A second rule runs in the unit lane with no build: nothing on the root-layout path may value-import the locale bodies, and the manifest must import nothing. **The budget failed on its own first gate run**: I calibrated `/` against a default build (the six-chunk gated teaser, 164 KB) while `gate.mjs` builds `PRIVATE_MODE=false`, where `/` is the real landing page at 247.4 KB — the `.204` asymmetry again, *the gate measures a configuration production does not serve*. Caps now set against what the gate builds, with the note at the constant. Three mutants killed. Tests 1061→1066.
- **Numbers the product overstates (`.208`):** two celebrations the app could not support. **Four filters for one quantity** — [`percentLoad.ts`](src/lib/workout/percentLoad.ts) says the prescriptions, the /benchmarks cards, the live PR chip and the debrief "all quote the same number", and they did not: the PR chip **included sets taken to failure** while the other three excluded them. Prior best bench 100×6 (e1RM 116.1); log 100×8 marked failure → 124.1 → the brass chip fires and `isPr` goes into the log, while the chart, the debrief and next session's prescribed load all still say 116.1 — verbatim the failure `benchmarks.ts:4-9` claims was already fixed. A set to failure gives the highest and least repeatable reading, which is *why* the three estimate consumers refuse it, so the celebration fired on the one set kind the rest of the app declines to trust. **The `drop` disagreement was left standing on purpose** — it is taste, not arithmetic (a drop set is evidence but the burnout is not a moment to celebrate), so the two reasons are now two names: `countsTowardStrengthEstimate` for what the app *believes*, `countsTowardPr` for what it *celebrates*. Flattening a deliberate choice to make a table tidy would have been the wrong fix. **The PR that could never not happen**: `estimateOneRepMax` returns 0 above 12 reps, so `getBestPriorSet` returned **null forever** for a high-rep-only athlete while `isPersonalRecord` answered `if (!prior) return true` — goblet squats at 20kg × 20 got the chip and the haptic on set one and on set two hundred, with `isPr` written to the log each time. Checking the *new* set first fixes it; the genuine first-estimable-set case still reads as a PR. Two existing tests encoded the old behaviour with no rationale; one was the bug written down. Three mutants killed. Tests 1058→1061. **Streak decay, planned for `.208`, is deliberately not here** — separate wrong number, wider blast radius (`StreakChip`, `WorkoutVictorySheet`, `computeWinScore`, leaderboard), carried forward.
- **The coach that thinks it is always Monday (`.207`):** `useCoachPlan` called `adaptPlan(existing, ctx, weekStart)` — the start of the week as **today** — so `todayDayOffset` was always `0`. Two live consequences: `dayOffset < todayOffset` never matched, so **no session was ever marked missed** and the "life happened, days re-spread" adaptation could not fire at all; and the low-readiness recovery swap targets `dayOffset === todayOffset`, so on a Thursday with readiness 30 the coach swapped **Monday's** session — already gone — and left Thursday's heavy squat day standing. The real date was in scope the whole time, three lines up. **The revision was a claim nobody had to earn**: `adaptPlan` returned `revision + 1` unconditionally and the hook guards its save with `next.revision !== existing.revision`, always true — so every mount rewrote the plan, called `scheduleCoachPush()`, and `hasCoachAdaptationSignal` (`revision > 1`) told **every athlete on every visit** that their week had been adapted when nothing had changed (`.127`). An unchanged week now returns the same object. **The cycle**: `savePlan` dispatches, the hook listens and calls `refresh()` which called `savePlan` — synchronous `dispatchEvent`, two consumers mounted in `HomeTodayDashboard`. **I did not execute it** (needs a browser and a React tree), so rather than claim a reproduction, [`adaptTermination.test.ts`](src/lib/coach/adaptTermination.test.ts) pins the property that closes it: `adaptPlan` is idempotent on **every day of the week**. **The vacuous assertion**: `adapt.test.ts`'s "marks past sessions missed" passed `today = weekStart` then asserted `missed.length >= 0` — true of every array ever created, green for the whole life of the bug it was named after. **One mutant survived first run and it was my own new guard** — `recovery-swap-hits-the-wrong-day`, because the test read `if (kind !== 'strength') return` and the fixture has no session on day 3 at all. Fifth vacuous guard in this programme; preconditions are now asserted, never skipped past. Tests 1049→1058.
- **Two controls that write a number nobody asked for (`.206`):** both the same shape — a control touched for one reason quietly writes a second value the athlete never entered. **Editing reps zeroed the prescribed weight**: `updateSetInput` rebuilt the whole `{reps, weight}` pair from `getSetInput(exIdx, setIdx, 10, 0)`, and `resolveSetInput` returns those defaults **verbatim** for a prescribed exercise — so a coached bench 3×5 @ 100kg tapped once on reps logged **6 × 0kg**, zero volume on the lift the coach asked for, and then `suggestNextSetTarget` computed next week from a set that never happened. Every other `getSetInput` call site passes `set.reps, set.weight`; this one alone passed `10, 0`, which is why the console *displayed* the prescription correctly right up to the moment it was edited. Second half: it read `setInputs` from the render closure not the updater's `prev`, and "Apply targets" fires two synchronous calls per set — so a 3×5 prefilled as **10 reps**, verbatim the `.175` bug its own comment claims was fixed. Rule extracted to [`nextSetInput`](src/lib/workout/activeWorkoutHelpers.ts) because the defect is a *shape* (`.196`). `activeWorkoutHelpers.test.ts` covered `resolveSetInput` thoroughly and **it was never wrong** — what broke was the arguments a caller handed it, which no test of a correct function can see. **Fuel logged your goal as your lunch**: `applyTargets` called `saveMacroTargets` (the whole job) and *also* unshifted a `Calc target protein 180g` row into `mw_nutrition_log`, which `NutritionPage` sums into the day's **consumed** totals — so a 2400 kcal target read as 2400 kcal eaten before any meal, and fed the 150g high-protein counter, inflating the Mission Score's Fuel pillar off a number the athlete only wished for (`.127` at the source). It also wrote `logs.slice(0, 50)`, the only row cap in the repo where every other writer keeps **90 days** — under two weeks of real use, so one tap deleted months of meals. `.170`'s rule one layer down: deleting the write fixes both, and the guard is stated repo-wide (pruned by age, never by row count). Four mutants killed. Tests 1041→1049.
- **The restore the app forgets, then destroys (`.205`):** the worst defect the `.204`–`.213` audits found — it destroys the data an athlete deliberately asked the app to protect. [`backup.ts`](src/lib/backup.ts) and [`importCsvRestore.ts`](src/lib/workout/importCsvRestore.ts) write the zustand persist payload straight to `WORKOUT_STORE_KEY` and, by design, leave the refresh to the caller (pure merge testable, browser half thin — that seam is right). Both callers ran `setTimeout(() => router.refresh(), 1200)`, and **`router.refresh()` preserves client-side React state by design**: the store was already hydrated, `persist` re-reads storage only on rehydrate, and nothing asked it to. So — new phone, restore 300 workouts, toast says *"300 workouts merged… Reloading…"*, **nothing reloads**, History still empty, the athlete logs one set, `persist` serialises its in-memory state over the file, and **all 300 workouts are gone permanently**. Identical for Strong/Hevy CSV import. [`backup.test.ts`](src/lib/backup.test.ts) covers `mergeBackup` thoroughly and could not see it, because **the merge was always correct** — the defect lived entirely in the sentence after it, which is why the guard reads call sites rather than merge results. New [`reloadAfterRestore.ts`](src/lib/storage/reloadAfterRestore.ts) names the rule and owns it: *a function that writes storage behind a live store must say how the store learns.* A full document reload, not `persist.rehydrate()` — rehydrating repopulates the store but leaves every module that cached a read at mount holding pre-restore values, and the copy had been promising a reload the whole time. The guard also pins the copy: a toast saying "Reloading…" must be attached to something that reloads. Two mutants, three failures each. **Process note:** my mutant cleanup used `git checkout --` on files holding uncommitted work and silently reverted the fix — second occurrence, after `.202`. The new guard caught it on the next run. Rule now explicit: **commit before mutating.** Tests 1035→1041.

Both now on shared [`todayGuidanceMount.ts`](src/lib/today/todayGuidanceMount.ts) (`.195` pattern; `i-day` still bare). One audit claim **refuted rather than fixed** — the lapsed-before-first-workout cohort needs no re-entry card, because `computeReentry` returns `NONE` for zero history on purpose. Four mutants killed; the redirect guard failed its own first run by matching the broken spelling inside the comment shipped with the fix — `ciTruth`'s workflow-header trap again.
